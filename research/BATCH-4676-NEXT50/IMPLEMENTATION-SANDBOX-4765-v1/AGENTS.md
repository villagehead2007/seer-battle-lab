# AGENTS.md

## 项目范围

这是一个本地赛尔号单挑对战实验台。浏览器界面由 `dist/app.js`、`dist/styles.css` 和 `dist/growth.css` 提供；对战计算、养成面板、行动顺序、伤害、异常、回合效果和技能执行位于 `dist/engine.js` 与 `dist/souls.js`。通用技能效果注册表是 `dist/effect-registry.js`，范围效果和结构化效果位于 `dist/range-effects.js`，魂印注册与事件分发位于 `dist/soul-registry.js`、`dist/range-souls.js` 和 `dist/souls.js`。

每只本地精灵保存为 `data/species/<id>.json`，由 `local-species.cjs` 校验和读取。文件必须包含真实种族值、属性克制表、全部技能、技能效果实例、魂印版本哈希和来源快照。`data/species-pending` 仅表示待部署资料，不能当作已完成精灵。

## 资料查询

首选 SeerAPI：`https://api.seerapi.com/v1/`。`seerapi.cjs` 通过 `pet`、`skill`、`skill_effect_type`、`element_type`、`element_type_combination` 和 `soulmark` 查询，并保存来源 URL、revision/hash 和加载时间。请求通过 `wiki-client.cjs` 串行排队、缓存并遵守冷却；不得用猜测值替代查询结果，不得执行 Wiki/API 返回的代码。BWIKI MediaWiki API 是备用来源，客户端规则见 `wiki-client.cjs`、`wiki-request.cjs` 和 `wiki-fetch.ps1`。

当 SeerAPI 与 Wiki（包括 BWIKI）对同一资料的描述、数值、参数或机制说明不一致时，统一采用 SeerAPI 的说法作为实现和审核依据，不因 Wiki 的不同说法反复请求用户裁决。保留双方原始资料、来源 URL、revision/hash 及差异记录，不改写来源。Wiki 仅用于补充 SeerAPI 未说明且不与其冲突的信息。SeerAPI 自身字段或接口之间的矛盾、缺失和歧义仍须继续查证，无法确认时再询问用户，不得以本条为由猜测或绕过验证。

资料不可访问时记录具体 HTTP/网络/解析原因，保留已有本地版本，不能伪造魂印、技能名称、效果参数或完成状态。

## 实现规范

每只精灵最终必须完整实现真实魂印、全部技能及实际对战效果；第一阶段按下文两阶段策略仅实现单精灵可触发部分：触发条件、概率、持续回合、先制/优先级、命中与暴击条件、免疫、消耗、目标范围、伤害类型、回血/禁疗、能力变化以及和其他效果的交互都要有代码依据。

技能效果先通过 `E.WIKI.assess` 和注册表编译为带 `effectId`、顺序、阶段和参数的指令。效果 ID 必须校验模板、参数数量和范围；重复效果必须保留顺序与各自参数。魂印 ID 与技能效果 ID 分开注册，魂印版本必须匹配来源 hash。复杂或多精灵目标效果不能写成单挑占位后宣称完成，应在 `deferredEffects`/待办文档中明确标记。

禁止只写入数据、只创建规则入口、静默忽略未知效果、删除断言、弱化测试或用表面 smoke test 宣称完成。没有针对触发条件和交互的验证时，状态只能写“待验证”。不要为了本批任务重构无关架构。

## 批处理流程

按 seer_id.txt 文件中的实际排列顺序处理，每批目标为10只。seer_id.txt 是唯一正式导入队列，不得根据精灵ID连续关系自动推算下一只精灵。只处理列表中存在的编。：查询真实资料，保存本地快照，实现单精灵魂印和技能分支，完整登记多精灵延期，做针对性测试，完成 10 只后做整批回归。无魂印且按当前项目策略跳过的编号必须记录为 skipped；不能把跳过当成已完成。每批结束更新 `PROGRESS.md`，分别列出单精灵阶段完成、全部机制完全完成、跳过、待验证、阻塞、多精灵延期和下一批起点。

### 精灵导入队列规则

`seer_id.txt` 是项目唯一正式导入队列。

1. 精灵处理顺序完全由 `seer_id.txt` 决定。
2. 不允许根据当前精灵ID自动选择下一只精灵。
3. 不允许处理不在 `seer_id.txt` 中的精灵，除非用户明确要求临时导入。
4. 临时导入的精灵：
   - 可以完成审核、实现和测试；
   - 完成后不得自动推进正式导入游标；
   - 如果用户希望正式纳入，必须先加入 `seer_id.txt`。
5. 新增精灵进入列表后，以文件中的实际位置作为后续顺序依据。
6. 中断恢复时，必须读取 `seer_id.txt` 和当前进度，而不是根据当前ID推算。
seer_id.txt 中的精灵默认均为正式导入目标，不应自行导入不在列表中的精灵。除非用户明确要求，否则不得根据连续 ID、外部资料或测试需求额外添加精灵。

## 赛尔号本地对战项目开发规范

### 数据真实性

必须严格查询 SeerAPI 的真实资料，使用精灵、魂印、技能、效果类型和属性克制表的实际返回值及版本标识。不得编造、猜测、改写或简化魂印、技能名称、效果参数和效果描述。SeerAPI 无法访问时记录具体原因并保留阻塞状态，不能用猜测数据补齐。

### 效果实现完整性

每个魂印和每个技能词条最终都必须实现真实对战行为，第一阶段必须完成其单精灵部分，包括触发条件、执行时机、概率、持续回合、先制和优先级、命中与暴击条件、免疫、消耗、目标范围、伤害/回复类型及其与其他效果的交互。只登记数据、只建立规则入口、返回空处理器或省略复杂机制都不算实现。多精灵或暂未支持的机制必须明确标为部分实现、未实现或 deferred。

### 测试标准

测试必须通过真实对战状态变化验证效果，例如体力、能力等级、异常状态、PP、优先级、回合计数、免疫和效果消费；不能只测试技能能释放、效果 ID 存在或编译成功。必须覆盖成功、失败、边界和关键交互分支。没有真实状态变化断言的测试只能作为结构检查，不能用来宣布词条完成。

### 批量交付

每 10 只精灵为一批，按 seer_id.txt 顺序逐只查询、完成单精灵部分并测试，不要求编号连续，列表中的编号顺序优先于数值大小。完整登记多精灵分支；完成第 10 只后运行整批回归测试，再更新 `PROGRESS.md`。单只 smoke 测试通过不等于该精灵或该批完成。

### 禁止行为

禁止占位实现、伪造测试通过、删除或弱化断言、擅自省略复杂机制、静默忽略未知词条，或把未完成、待验证、部分实现和阻塞中的精灵标记为完成。不得为绕过失败而删除正确代码或修改与当前任务无关的功能。

### 进度管理

持续维护 `PROGRESS.md`，准确区分已完成、待验证、部分实现、未实现、跳过和阻塞。记录真实失败、影响范围、已尝试修复和下一步任务；资料接入、代码存在或基础测试通过都不能单独改变完成状态。

### 执行效率

优先推进真实资料查询、代码实现和必要测试，避免无限规划或反复纠结与当前工作无关的失败。单个问题最多连续尝试三种修复方案；仍然失败时记录阻塞原因，继续处理不依赖该问题的独立词条，并在批次回归中如实报告。

## 两阶段策略覆盖（当前规则）

当前采用“先单精灵、后多精灵”策略。本节覆盖前文中要求第一阶段必须实现多精灵效果才可推进的表述。第一阶段只要求当前精灵与当前对手在场时可触发的真实魂印、技能和效果，包括伤害、属性变化、异常状态、回合效果、先制、命中、暴击、消耗和免疫。换宠、队伍、下一只出场、队友、场下精灵和队伍存活数量属于第二阶段，暂不实现。

混合词条必须按真实语义拆分：单精灵分支立即实现并通过状态变化测试，多精灵分支保留原始描述、效果 ID、实例参数、触发条件、来源 URL、revision/hash 和未来所需机制，并登记到统一 `MULTI-PET-TODO.json`/`MULTI-PET-TODO.md`。不得仅凭效果 ID 判断延期范围。未核实语义的条目只能标为待审核，不能据此豁免单精灵实现。

“单精灵阶段完成”要求所有单精灵分支真实实现、专项状态变化测试通过、完整 `npm test` 通过，并且每个多精灵分支已完整登记；它不等于“全部机制完全完成”。完成第一阶段允许推进游标，延期多精灵分支不进入单精灵 `pendingEffects` 或外部阻塞回访队列。全部精灵完成第一阶段后，才开始第二阶段多精灵引擎和延期词条实现。`automation-validate.cjs <id>` 检查单精灵阶段，`automation-validate.cjs <id> --complete` 才检查全部机制完全完成。历史“已完成”不自动视为经过新标准认证。

具体审核字段、命令及调度规则见 `DEVELOPMENT-STAGES.md`。本次策略迁移保持自动开发暂停，不使用 Git。

## 伙伴效果与羁绊效果分类规则

伙伴、羁绊、觉醒等名称或解锁方式不构成多精灵依赖。伙伴效果和羁绊效果属于精灵自身强化系统，默认在单精灵阶段实现并验证，不得仅因名称、获取条件或现有引擎缺口登记到 MULTI-PET-TODO。

只有来源原文明示依赖队伍成员、替补精灵、下一只精灵出场、换宠流程、场下精灵状态、队伍数量或队伍共享状态的分支才可延期。审核必须指出原文中的具体依赖和触发条件；不能用“伙伴系统尚未支持”等实现限制代替来源证据。

- 伙伴追加技能：使用真实ID、来源版本及实例参数加入该精灵技能列表，接受技能基础行为和逐效果状态测试。
- 伙伴提供的技能强化：作为该精灵可使用能力实现，覆盖激活条件、消耗、时序及交互。
- 羁绊强化魂印/觉醒魂印：保留原魂印与强化魂印两个真实版本，分别保存来源hash、参数和审核证据，并测试版本选择与真实战斗行为；不得覆盖原始数据或猜造版本。
- 混合效果：自身强化部分当前实现并验证；真正依赖队伍或其他精灵的部分独立登记延期。

缺少可确认资料的自身强化仍是单精灵待审核/阻塞项，不能靠延期绕过。该分类只增加审核约束，不减少来源、参数、成功/失败/边界/交互断言或整库回归要求。

## 保留1HP与伤害事件（用户确认Q-DAMAGE-001，2026-10-19）

保留1HP只限制最终HP，不截断完整结算伤害。
例如200HP受到结算后800伤害，保命后剩1HP，完整伤害仍记录800，实际HP减少量为199。

原本只有1HP，受到正数结算伤害后因保命仍为1HP时，完整伤害仍按正常结算记录，并触发按“受到伤害”判断的事件；明确要求“实际失去体力”的效果则不触发。

这不意味着免疫、完全抵挡等造成结算伤害为0的情况也触发正伤害事件。明确写明限制伤害数值的机制仍按其具体规则处理。
